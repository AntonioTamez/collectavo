From RESEARCH.md Pattern 5 — Raw SQL to append to migration file:
The generated migration SQL will have all CREATE TABLE and CREATE INDEX statements from the schema.
After prisma migrate dev generates the file, append these SQL statements at the END of the migration.sql:

  CREATE OR REPLACE FUNCTION products_search_vector_update()
  RETURNS trigger AS $$
  BEGIN
    NEW."searchVector" := to_tsvector(
      'english',
      coalesce(NEW.title, '') || ' ' || coalesce(NEW.description, '')
    );
    RETURN NEW;
  END;
  $$ LANGUAGE plpgsql;

  CREATE TRIGGER products_search_vector_trigger
  BEFORE INSERT OR UPDATE ON "products"
  FOR EACH ROW EXECUTE FUNCTION products_search_vector_update();

Note: Do NOT add a manual CREATE INDEX for searchVector — the @@index([searchVector], type: Gin) in schema.prisma should generate this DDL. Verify after migration by checking \d products in psql.

From RESEARCH.md Developer Workflow:
  Step 1: docker compose exec core-api npx prisma migrate dev --name init
  Step 2: [Edit migration.sql to append tsvector trigger — see Pattern 5]
  Step 3: docker compose exec core-api npx prisma migrate dev --name add_tsvector_trigger
    (OR: re-run migrate dev if the migration was not yet applied — Prisma will re-apply pending files)
  Step 4: docker compose exec core-api npx prisma db seed

IMPORTANT workflow clarification:
The tsvector trigger must be in the INITIAL migration so it fires from the first INSERT.
Best approach: Run `prisma migrate dev --name init` to generate migration.sql, then IMMEDIATELY (before running any other migration) append the trigger SQL to the generated file, then run `prisma migrate dev` again — Prisma detects the file is not yet applied and applies it with the trigger included.

Alternative (simpler): If the GIN index from @@index([searchVector], type: Gin) is already in the generated migration.sql, only the trigger function and trigger definition need to be appended. Run only ONE migrate dev — append to the file FIRST, then apply.

From RESEARCH.md Pitfall 3:

Check docker compose ps to confirm postgres status shows "healthy".

From RESEARCH.md Pitfall 4 (migration drift warning):
